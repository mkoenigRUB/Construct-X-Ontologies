Construct-X · Beispiel Datenaustausch

Doppelboden – Dokumentation und Beispieldaten

Dieses Beispiel zeigt einen einfachen Datenaustausch zwischen zwei Projektbeteiligten im Rahmen von Construct-X. Ein Auftraggeber fordert für den Doppelboden eines Bauprojekts eine detaillierte Feinterminplanung an. Die Anforderung wird als Notification übertragen und verweist über contextResource auf einen separaten fachlichen Datensatz mit den zugehörigen Planungsinformationen.

Notification als JSONData Content als JSONKlare Referenz über PCS-001

1. Beispiel und Zielsetzung

Das Beispiel demonstriert die Trennung zwischen einer operativen Nachricht und dem dazugehörigen fachlichen Data Content. Die Notification beschreibt, welche Information angefordert wird. Der eigentliche fachliche Inhalt wird in einer separaten Ressource bereitgestellt.

Im konkreten Fall wird für den Doppelboden eine Feinterminplanung angefordert. Die Notification benennt den Task-Typ DetailedScheduling und verweist mit contextResource auf den Datensatz PCS-001. Dieser Datensatz enthält die für die weitere Bearbeitung relevanten Planungsinformationen.

Grundidee: Die Notification bleibt klein und transportiert nur die zur Steuerung des Vorgangs notwendigen Informationen. Umfangreichere fachliche Daten werden separat über eine referenzierte Ressource ausgetauscht.

2. Grundlage: Tractus-X Industry Core KIT

Das Notification-Muster dieses Beispiels orientiert sich an der standardisierten Notification-Architektur des Tractus-X Industry Core KIT bzw. an CX-0151 Industry Core: Basics. Dort werden Notifications als JSON-Nachrichten mit zwei klar getrennten Bereichen beschrieben: einem standardisierten header und einem anwendungsspezifischen content. Die Übertragung erfolgt über einen Dataspace Connector.

Construct-X übernimmt in diesem Beispiel dieses technische Grundmuster. Der Header folgt der aus Tractus-X bekannten Struktur; die fachlichen Inhalte im Bereich content sind dagegen Construct-X-spezifisch. Insbesondere ist contextResource keine Vorgabe des Industry Core KIT, sondern eine Construct-X-spezifische Referenz auf den separat bereitgestellten fachlichen Data Content.

Industry-Core-ElementUmsetzung im Beispiel
header.messageIdVerwendet; eindeutige Nachrichten-ID als UUID-URN.
header.contextVerwendet; ConstructX-NotificationAPI-TaskRequest:1.0.0 kennzeichnet Notification API, Operation und API-Version.
header.sentDateTimeVerwendet; Zeitstempel im ISO-8601-Format mit Zeitzone.
header.senderBpnVerwendet; im Beispiel mit einer synthetischen BPNL.
header.receiverBpnVerwendet; im Beispiel mit einer synthetischen BPNL.
header.expectedResponseByVerwendet; optionale Frist für die erwartete Reaktion.
header.versionVerwendet; 3.0.0 entsprechend dem in Tractus-X verbreiteten Message-Header-Modell.
contentUse-Case-spezifisch; enthält die Construct-X-Fachinformation zur angeforderten Feinterminplanung.
Abgrenzung: Das Beispiel übernimmt das Industry-Core-Notification-Muster für den JSON-Payload. Eine vollständige Notification API umfasst darüber hinaus die Definition der unterstützten Operationen, HTTP-Endpunkte und Rückgabecodes sowie die Registrierung eines passenden Connector-Assets einschließlich Asset-Eigenschaften und Policies. Diese Infrastrukturartefakte sind nicht Gegenstand des vorliegenden Beispieldatenpakets.

3. Austauschstruktur

Notificationnotification/doppelboden-task-request.json

Anforderung einer Feinterminplanung für den Doppelboden.

→
Data Contentdata/doppelboden-planning-context.json

Fachlicher Datensatz PCS-001 mit den Planungsinformationen.

Verknüpfung: Der Wert von content.contextResource in der Notification entspricht der id des fachlichen Datensatzes.

4. Paketinhalt

construct-x-doppelboden-beispieldaten/ ├── documentation.html ├── notification/ │ └── doppelboden-task-request.json └── data/ └── doppelboden-planning-context.json

5. Notification

Die Datei doppelboden-task-request.json ist die operative Nachricht zwischen den beteiligten Systemen. Ihre Grundstruktur folgt dem Tractus-X Industry Core KIT: Der standardisierte header enthält die technischen Nachrichtendaten; unter content liegt der Construct-X-spezifische fachliche Notification Content.

Für das Beispiel sind insbesondere folgende Angaben relevant:

  • notificationType = TaskRequested – es wird eine Aufgabe bzw. Zuarbeit angefordert.
  • taskType = DetailedScheduling – Gegenstand der Anforderung ist eine detaillierte Terminplanung.
  • subjectRole = Target – die referenzierte Ressource ist Ziel bzw. Gegenstand der Aufgabe.
  • contextResource = …/PCS-001 – Verweis auf den zugehörigen fachlichen Datensatz.

Beispiel der Referenz

{ "content": { "notificationType": "TaskRequested", "taskType": "DetailedScheduling", "contextResource": "https://data.general-contractor.example/project/PROJECT-X/exchange/package/PCS-001" }
}

6. Data Content

Die Datei doppelboden-planning-context.json enthält den eigentlichen fachlichen Payload. Sie bildet den Planungskontext ab, den der Empfänger benötigt, um die angeforderte Feinterminplanung für die Doppelbodenarbeiten auszuarbeiten. Der Datensatz wird unabhängig von der Notification als eigene Ressource über den Datenraum bereitgestellt oder abgerufen.

Der Data Content ist durch die Kennung PCS-001 eindeutig identifiziert. Genau diese Ressource wird in der Notification über content.contextResource referenziert.

{ "id": "https://data.general-contractor.example/project/PROJECT-X/exchange/package/PCS-001", "identifier": "PCS-001", "semanticModel": { "type": "PlanningContext", "conformsTo": [ "…" ] }, "content": { "entities": [ … ] }
}

6.1 Aufbau des Payloads

BereichBedeutung
idEindeutige URI des bereitgestellten Datensatzes. Diese URI ist zugleich das Ziel von contextResource in der Notification.
identifierKompakte fachliche Kennung des Datensatzes, hier PCS-001.
semanticModelBeschreibt den Typ des Datensatzes und referenziert über conformsTo die semantischen Construct-X-Modelle, nach denen die Inhalte strukturiert sind.
content.entitiesEnthält die fachlichen Objekte des Planungskontexts. Jedes Objekt besitzt eine eigene ID, einen Typ und die für diesen Objekttyp relevanten Eigenschaften und Beziehungen.

6.2 Inhalt des Planning Context

Der Planning Context enthält nicht nur die Zielaktivität selbst, sondern auch die Informationen, die für ihre detaillierte Terminierung und Ausführung relevant sind. Im Beispiel umfasst der Datensatz 47 miteinander verknüpfte fachliche Objekte.

InformationsbereichBeispielinhaltBedeutung für die Feinterminplanung
TerminplanRahmenterminplan SCH-01, Aktivität A100 „Einbau eines Doppelbodens“Vorgabe des übergeordneten Zeitfensters, das durch den Nachunternehmer weiter detailliert werden soll.
VorgängerbeziehungA090 „TGA-Rohinstallation im Bodenhohlraum abschließen“ → A100, Beziehung FinishToStartZeigt die terminliche Abhängigkeit, die bei der Feinterminplanung berücksichtigt werden muss.
LeistungsverzeichnisLV-Position 03.02.010 „Doppelboden liefern und einbauen“, Menge 300 m²Verknüpft die auszuführende Leistung und Menge mit der Terminplanaktivität.
ProjektstrukturWBS-Zuordnung „Doppelboden“ und LBS-Zuordnung „5. Obergeschoss“Ordnet die Aktivität fachlich und räumlich in das Projekt ein.
ArbeitsflächeWORK-05OG – Arbeitsbereich Doppelboden im 5. OGBeschreibt den für die Ausführung vorgesehenen Arbeitsbereich.
LagerflächeSTORAGE-EXT-01 – Außenlagerfläche, u. a. 50 m² nutzbare Fläche und 25 m Entfernung zum BauaufzugLiefert Randbedingungen für Materialbereitstellung und Baustellenlogistik.
BauaufzugLIFT-01 – Bauaufzug mit Verfügbarkeit im Ausführungszeitraum, Nutzlast, Plattformabmessungen und bedienten EbenenErmöglicht die Berücksichtigung des vertikalen Materialtransports bei der Ablaufplanung.

6.3 Zielaktivität A100

Im Zentrum des Datensatzes steht die Aktivität A100 „Einbau eines Doppelbodens“. Sie ist im Rahmenterminplan für den Zeitraum vom 8. März 2027, 07:00 Uhr bis zum 19. März 2027, 16:00 Uhr vorgesehen. Dieses Zeitfenster stellt den Rahmen dar, innerhalb dessen der Nachunternehmer seine detaillierte Ablauf- und Ressourcenplanung erstellen soll.

Mit A100 sind unter anderem folgende Informationen verknüpft:

  • fachliche Einordnung in die Work Breakdown Structure,
  • räumliche Zuordnung zum 5. Obergeschoss über die Location Breakdown Structure,
  • die LV-Menge von 300 m² Doppelboden,
  • die Vorgängeraktivität A090,
  • Arbeits-, Lager- und Aufstellflächen,
  • der für die Ausführung vorgesehene Bauaufzug einschließlich logistischer und technischer Eigenschaften.

6.4 Semantische Verknüpfung der Inhalte

Die einzelnen Objekte stehen nicht isoliert nebeneinander. Sie werden über ihre IDs miteinander verknüpft. So verweist beispielsweise der Quantity Split der LV-Position auf die Aktivität A100, die Aktivität auf die benötigten Flächenzuordnungen und die Flächenzuordnung wiederum auf konkrete Baustellenflächen. Auf diese Weise entsteht ein zusammenhängender Planungskontext, der von Anwendungen maschinell ausgewertet werden kann.

Das Feld semanticModel.conformsTo enthält die Referenzen auf die verwendeten Construct-X-Ontologien und Shapes, beispielsweise für Terminplanung, Baustellenlogistik, GAEB/BoQ sowie WBS- und LBS-Verknüpfungen. Die eigentlichen Ontologiedateien müssen dafür nicht Bestandteil dieses Beispielpakets sein.

6.5 Warum der Data Content separat übertragen wird

Die Trennung von Notification und Data Content erlaubt es, die Nachricht klein und stabil zu halten. Die Notification signalisiert den fachlichen Vorgang und verweist auf den benötigten Kontext. Der Data Content kann dagegen unabhängig bereitgestellt, aktualisiert, versioniert und mit eigenen Zugriffsregeln versehen werden. Der Empfänger lädt nur den Datensatz, den er zur Bearbeitung der Aufgabe benötigt.

7. Ablauf des Datenaustauschs

  1. Der Sender erzeugt die Notification doppelboden-task-request.json.
  2. Die Notification wird über den Connector an den Empfänger übertragen bzw. für ihn bereitgestellt.
  3. Der Empfänger liest content.contextResource.
  4. Über diese Referenz wird der fachliche Datensatz PCS-001 identifiziert.
  5. Der Data Content doppelboden-planning-context.json wird separat bereitgestellt oder abgerufen und kann anschließend verarbeitet werden.

8. Rolle der beiden Beispieldateien

DateiRolle
notification/doppelboden-task-request.jsonOperative Nachricht zur Anforderung der Feinterminplanung.
data/doppelboden-planning-context.jsonFachlicher Datensatz mit den zugehörigen Planungsinformationen.

Durch diese Trennung können Notifications klein und eindeutig bleiben, während fachliche Daten unabhängig davon verwaltet, versioniert und über den Datenraum bereitgestellt werden können.
